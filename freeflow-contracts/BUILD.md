# FreeFlow Contracts — Build Guide

This document is the authoritative reference for building the five Solana programs
in this workspace. Read it before touching the build toolchain.

---

## Quick start (correct commands)

```bash
# From WSL Ubuntu only — NOT Windows-native PowerShell or cmd
export PATH="/root/.local/share/solana/install/active_release/bin:/root/.cargo/bin:$PATH"
export HOME=/root
cd /mnt/d/Solana/freeflow-contracts

# Build all five programs
anchor build --no-idl

# Build one program (e.g. repflow-token)
anchor build --no-idl -p repflow_token
```

That is the complete build. Nothing else is needed.

## Why `anchor build --no-idl` and not `cargo build-sbf`

### The `--no-idl` flag

Two of the five programs (`registry`, `rewards`) use the raw Solana `entrypoint!`
macro instead of Anchor's `#[program]` macro. Anchor cannot extract an IDL from
these programs and exits with `Error: IDL doesn't exist`, stopping the entire build.

**Always pass `--no-idl`.**  The IDL files that DO exist (`target/idl/`) are
hand-maintained and not generated by the build.

### Why not `cargo build-sbf --manifest-path`

`cargo-build-sbf` calls the Solana platform-tools `cargo` (version **1.79.0**).
Cargo 1.79 cannot parse `Cargo.toml` files that declare `edition = "2024"`.
Several transitive dependencies in the anchor/SPL dependency tree pulled in
packages with edition2024 manifests (notably `indexmap ≥ 2.14.0`).

`anchor build` routes through the same `cargo-build-sbf` but honours the
workspace `Cargo.lock`, which is pinned to safe versions (see next section).
Running `cargo-build-sbf` directly bypasses this and re-resolves, picking up
the unsafe versions.

## The Cargo.lock and why it is committed

**`Cargo.lock` is committed in this repository.** This is intentional.

### Background

Solana `platform-tools v1.43` ships `rustc 1.79.0` and `cargo 1.79.0`.
Cargo 1.79 cannot compile any crate whose own `Cargo.toml` uses
`edition = "2024"`. The following packages (reachable via the anchor-lang
transitive dependency graph) adopted edition2024 at these version thresholds:

| Package | Safe (≤) | Breaks at |
|---|---|---|
| `indexmap` | `2.7.0` | `2.14.0` |
| `proc-macro-crate` | `3.1.0` | `3.5.0` (pulls `toml_edit 0.25 → indexmap ^2.13`) |
| `unicode-segmentation` | `1.12.0` | `1.13.2` |

The full breakage chain:
```
proc-macro-crate 3.5.0
  └── toml_edit 0.25.x
        └── indexmap ^2.13.0   ← edition2024, cargo 1.79 cannot parse
```

By committing `Cargo.lock` with these packages pinned to their safe versions,
every build is reproducible without manual intervention.

### If the lockfile ever gets out of sync

Symptoms: `anchor build` prints `feature 'edition2024' is required` or
`rustc X.Y.Z is not supported by package Z`.

Fix with the default cargo (1.95+), **not** the Solana cargo:

```bash
# Downgrade indexmap
/root/.cargo/bin/cargo update -p indexmap --precise 2.7.0

# Downgrade proc-macro-crate (specify version because 0.1.5 also exists)
/root/.cargo/bin/cargo update --precise 3.1.0 "proc-macro-crate@3.5.0"

# Downgrade unicode-segmentation
/root/.cargo/bin/cargo update -p unicode-segmentation --precise 1.12.0

# Verify
grep -A1 'name = "indexmap"' Cargo.lock
# Should show: version = "2.7.0"
```

Then commit the updated `Cargo.lock`.

### Never delete Cargo.lock

Running `rm Cargo.lock` and then `anchor build` will re-resolve all dependencies
and silently pick up the incompatible versions again. If you need a fresh resolve,
use the targeted `cargo update --precise` commands above instead.

## Workspace dependency pins

`Cargo.toml` `[workspace.dependencies]` documents the intent behind each pin.
Pins in `[workspace.dependencies]` alone do **not** propagate to transitive
dependencies — they only apply when a program crate explicitly uses
`{ workspace = true }`. The actual enforcement is through `Cargo.lock`.

Both must stay in sync. If you bump a pin in `Cargo.toml`, run the matching
`cargo update --precise` command and commit the updated lock.

## Troubleshooting

### `feature 'edition2024' is required`

The lockfile resolved an incompatible package version. Run the fix commands in
the **"If the lockfile ever gets out of sync"** section above.

### `anchor-lang version(0.30.0) and CLI version(0.30.1) don't match`

This is a **warning, not an error**. The programs depend on `anchor-lang 0.30.0`
but the installed CLI is `0.30.1`. The compiled output is correct. Suppress it
by adding `anchor_version = "0.30.0"` under `[toolchain]` in `Anchor.toml`
(not done yet because the version mismatch is harmless).

### `Error: IDL doesn't exist`

Caused by running `anchor build` without `--no-idl`. The raw-entrypoint programs
cannot generate IDLs. Always use `anchor build --no-idl`.

### `cargo-build-sbf: --locked: not a valid flag`

`cargo-build-sbf` does not support `--locked` as a direct flag. Pass extra cargo
arguments via anchor: `anchor build --no-idl -- --some-cargo-flag`. For lockfile
enforcement, rely on the committed `Cargo.lock` being present rather than flags.

### Build only updates one `.so`, others are cached

This is correct incremental behaviour — cargo only recompiles changed crates.
If you need to force a full rebuild (e.g. after a toolchain upgrade):

```bash
rm -rf target/sbf-solana-solana/release/
anchor build --no-idl
```

Do **not** delete `target/deploy/*.so` — they are the final artefacts.
Do **not** delete `Cargo.lock`.

### `lock file version 4 requires -Znext-lockfile-bump`

Cargo 1.79 (Solana platform-tools) cannot read Cargo.lock version 4. This
happens when cargo 1.95+ regenerates the lock file (version 4 is the default
in newer cargo). The fix is to manually change the lock file header:

```
# Change this line:
version = 4
# To:
version = 3
```

Then commit the updated `Cargo.lock`. The package entries are identical between
versions 3 and 4 — only the header version number differs.

### `rewards-keypair.json` is not the deployed rewards program

**The `target/deploy/rewards-keypair.json` keypair generates pubkey
`4QToanmYAk16WiBYYPEAR68pNsupg7CnHvWVqnVBuhce`, NOT the deployed program
`2yeVew5qq5jf5zuoqiE2svVLRE9HTN6J2GfB9LopdM1C`.**

The rewards program was originally deployed with a different keypair that is no
longer present in the repo. Always deploy upgrades using the program's on-chain
address string, NOT the keypair file:

```bash
# CORRECT — use the deployed program ID string
solana program deploy target/deploy/rewards.so \
  --url devnet --keypair $WALLET \
  --program-id 2yeVew5qq5jf5zuoqiE2svVLRE9HTN6J2GfB9LopdM1C

# WRONG — this creates/upgrades a different program at 4QToanmYAk16...
solana program deploy target/deploy/rewards.so \
  --url devnet --keypair $WALLET \
  --program-id target/deploy/rewards-keypair.json
```

This applies to any program whose keypair file was lost after the original deploy.
Always verify with `solana-keygen pubkey <keypair.json>` before upgrading.
